- **A 方**：`ecd_epitope_scanner`（本仓库，下称「你的方案」）

我的管线在文档里坦承"只能作粗筛闸门，短名单需用 FoldX/Rosetta 复算"——
而你的方案**把这一步直接做进了主流程**。这是代差，不是风格差异。

证据：`stability.py:243-305`（FoldX）、`stability.py:181-240`（EvoEF2）。

### 2.2 三级漏斗的突变设计（优于我的"策略枚举"）

`design.py` 的流程：

```
19 种替换全扫描（启发式预筛，可审计）
   ↓ 每点取 top-3
FoldX 单点筛选（ΔΔG ≤ +0.46 kcal/mol 才准入）
   ↓
组合搜索（2–5 点，空间分散 ≥5.5 Å，联合风险约束）
   ↓
FoldX BuildModel 复校（5 runs，取中位数）
```

对比我的 `design.py`：按策略（core/deep/shield/charge_invert/ala_strip/loop_replace）
枚举位点，用启发式 `combo_ddg` 把关，**全程没有物理引擎**。
你的"每点看全部 19 种替换"也比我的"每点只给 1 个默认目标（Ala/Ser）"信息量大得多。

### 2.3 "不编造兜底"的工程哲学


### 2.4 结构语义化的分区（比我的纯几何分区更有生物意义）

`partitioning.py` 的分区约束是我没有的：

- **跨域惩罚**：不同结构域连边 +4.0，不同二级结构 +1.5（边界尊重结构域/SSE）
- **膜方向分类**：以 `membrane_anchor_position` 为锚，按膜距离 33%/67% 分位
  分为 membrane-proximal / middle ECD / membrane-distal
- **域间配额分配**：按各结构域残基数比例分配区域数（最大余数法，`_allocate_quotas`）
- **连通性保证**：孤立表面岛连到最近邻，确保每个残基恰好归属一次
- **小区域合并**：<3 残基的区域并入最近区域

我的 `partition.py` 是测地距离 + KMedoids + silhouette 评估，目标固定 4 区，
**没有结构域和膜方向约束**。你的分区更能对应"一块有生物学含义的表面补丁"。

### 2.5 二硫键：注释 + 坐标双验证


### 2.6 序列输出更实验友好

- 有原始 CDS 时**只替换突变密码子**，其余保留天然序列（`sequences.py:130-135`）

我的 `dna.py` 总是全序列重新反向翻译（top codon only），

## 3. 发现的问题（按严重度排序）

### P0-1 · FoldX 输出解析 bug：表头行被当成 ΔΔG

`score_many_with_foldx` / `score_with_foldx` 的解析逻辑（`stability.py:291-305`、`:362-380`）：

```python
for path in temp.glob("Dif_*.fxout"):
    for line in ...:
        if not stripped or stripped.startswith(("#", "Pdb", "SD")):
            continue
        fields = re.split(r"\s+", stripped)
        values.append(float(fields[1]))
```

它只跳过了 `#` / `Pdb` / `SD` 开头的行，但 FoldX 5.1 的 `Dif_*.fxout` 第一句是：

```
FoldX 5.1 (2011)
```

`re.split` 后 `fields = ["FoldX", "5.1", "(2011)"]` → `fields[1] = "5.1"` →
**被解析成 ΔΔG = 5.1 kcal/mol**。

实测复现（用你的 `vendor/foldx/foldx_1_20270131.exe` 跑 `LA231D`）：

```
[解析]    FoldX 5.1 (2011)                     -> 误判为 dDG=5.1     ← 污染
[过滤]    Pdb	total energy	Backbone Hbond	...  -> 跳过
[解析]    structure_Repair_1_0.pdb	-0.597033  -> 真实值
[解析]    structure_Repair_1_1.pdb	-0.780479  -> 真实值
```

**后果**：`values = [5.1, ...真值...]`。走中位数分块时
`median(values[0:runs])` 会把 5.1 卷进**第一个区域**的评分，
使其被系统性抬高 → 合格设计被误判为超阈值（`> 0.46` → `FOLDX_REVIEW_REQUIRED`）。

**修复**（任选，建议 1+2）：

```python
# 1) 只接受以 .pdb 结尾、且首字段能解析为浮点的数据行
if not stripped.endswith(".pdb") and not re.match(r"^\S+\.pdb\b", stripped):
    continue

# 2) 更稳妥：显式定位表头，取其后所有行
lines = path.read_text(...).splitlines()
start = next(i for i, l in enumerate(lines) if l.startswith("Pdb\t"))
for line in lines[start + 1:]:
    ...
```

### P0-2 · `stability_engine` 字段与真实来源矛盾

`test_output/foldx_ecd/designs.json` 第一条记录：

| 字段 | 值 |
|---|---|
| `status` | `FOLDX_REVIEW_REQUIRED` |
| `stability_engine` | **`FoldX 5.1`** |
| `combined_stability_score` | **`2.7954`** |
| `warnings` | "the reported score is a dimensionless within-target structural-risk proxy, not kcal/mol" |
| `warnings` | "FoldX BuildModel output could not be parsed; no stability conclusion was assigned." |

即：FoldX 解析失败 → 分数仍是**无量纲代理分**，但 `stability_engine` 字段写着 **FoldX 5.1**。
任何读这个字段的下游（包括前端）都会把 2.7954 当成 kcal/mol ——
那意味着"灾难性不稳定"，而真实含义完全不同。

这直接违反 README 第 75 行的承诺：
> "不会把代理分数写成 kcal/mol"

**修复**：分数来源与引擎名必须同源。解析失败时应把引擎名回退为
`"builtin structural-risk proxy (FoldX unavailable)"`，而不是保留 `FoldX 5.1`。
建议用一个 `score_origin` 字段显式区分 `foldx | evoef2 | proxy`。

### P1-3 · FoldX 在实测中一次都没成功过 —— 已定因并修复（2026-09-04）

统计所有已产出结果：

| 运行 | 区域数 | 状态 | 分数 |
|---|---|---|---|
| `test_output/foldx_ecd` | 5 | **全部 FOLDX_REVIEW_REQUIRED** | 2.80 / 2.06 / 0.97 / 0.96 / 0.94 |
| `test_output/online_q9nzq7` | 5 | 全部 RECOMMENDED | 2.80 / 2.06 / 0.97 / 0.96 / 0.94 |
| `test_output/pdl1` | 6 | 全部 RECOMMENDED | 2.71 / 1.79 / 1.99 / 1.26 / 0.66 / 0.81 |

两组分数**完全相同**，说明 FoldX 从未真正写入评分。进一步检查：
`foldx_ecd` 第一条记录的 152 个单点扫描里，**`foldx_ddg` 有值 = 0，None = 152**。

**根因（2026-09-04 定论）**：逐项排查（解析器、二进制、批量格式、输入结构、rotabase）
单独验证全部正常后，实跑整条管线捕获真凶——`score_many_with_foldx` 用
`TemporaryDirectory` 造运行目录，BuildModel **成功产出评分后**，清理阶段 rmtree
约 71 个文件触发宿主沙箱的批量删除保护，**进程被硬杀（EXIT=1，无 traceback）**，
评分随临时目录一起丢失。修复：`stability.py` 改用持久的
`engine_runs/<prefix>_<hash>/` 运行目录（不自动删除，兼作引擎失败诊断材料），
并在批量全部失败时抛 `ERROR_FOLDX_ENGINE`（fail-loud）而非静默降级。

**修复后实跑验收**（`test_output/foldx_verified3`，PD-L1/8AOM 全链路）：
5 区组合全部 `score_origin=foldx`、真实 kcal/mol
（+0.02 / −0.05 / −0.23 / −1.17 / −1.19）、5/5 返回 0 失败、
全部 `RECOMMENDED_LOW_PREDICTED_RISK`；单点 foldx_ddg 57 个有值；
诊断与 `sasa_method` 已写入 `run_manifest.json`。

### P1-4 · SASA 两条路径口径不一致，导致阈值含义漂移

`calculate_sasa`（`structure_analysis.py:416-434`）：FreeSASA 优先，Bio.PDB 回退。

- 参考表 `MAX_ASA` = Tien 2013（**DSSP 口径**：C 1.80 / N 1.60 / **O 1.40** / S 1.85）
- Bio.PDB `ATOMIC_RADII` = **Bondi 1964**（C 1.70 / N 1.55 / **O 1.52** / S 1.80）

实测确认（你的 venv，biopython 1.87）：
```
Bio.PDB ATOMIC_RADII:  C 1.7   N 1.55   O 1.52   S 1.8
→ Bondi 1964 口径 (O=1.52)
```

O 半径 1.52 vs 1.40 差 8.6%，富 O 侧链（D/E/N/Q/S/T）的 SASA 会系统性偏大 →
`rsasa >= 0.25` 这个硬闸门在两条路径下**选出不同的残基**，
而 `run_manifest.json` 未记录本次用的是哪条路径（只记了 biopython/numpy 版本）。

这正是我上一轮在自己管线里修掉的同一类问题（P1：Bondi → Chothia 统一口径）。

**修复**：
```python
# 1) 回退路径显式指定与参考表同口径的半径
ShrakeRupley(probe_radius=1.4, n_points=960,
             radii_dict={"C":1.80,"N":1.60,"O":1.40,"S":1.85})
# 2) FreeSASA 显式指定 radii
freesasa.Parameters({"algorithm": freesasa.ShrakeRupley,
                     "n-points": 960, "probe-radius": 1.4,
                     "radii": "naccess"})
# 3) 把 sasa_method 写进 run_manifest.json
```

### P2-5 · 组合突变沿用单点阈值（+0.46 kcal/mol）过严

`stability.py:410` 显示单点与组合用同一阈值。但 FoldX 的 ΔΔG 对多点突变
近似可加，5 点组合几乎不可能每点都 ≤0.46 且总和 ≤0.46。
从你的实测看，5 点组合的代理分普遍在 0.9–2.8 区间，门槛下**极可能全军覆没**。

我自己的管线对组合用 `combo_ddg_max = 3.5 kcal/mol`（单点 `ddg_max` 另设），
并对 ≤6 Å 邻近对打 25% 空间折扣（`coupling_discount`）。
建议你区分单点门与组合门，并引入类似的空间耦合折扣。

### P2-6 · 其他

- **`rest.uniprot.org` 依赖**：`retrieval.py:11`。该域在部分网络环境被阻断
  （我的环境即不可达，已改用 EBI Proteins API）。若需跨环境部署，建议加备用源。

  biopython/numpy/networkx 版本，也应记录 FoldX/EvoEF2 的路径、版本与本次是否启用。

  P0-1 这类解析 bug 正是单元测试最容易捕获的类型。
